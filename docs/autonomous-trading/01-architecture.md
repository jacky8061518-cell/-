# 01 底層架構

## 1. 分層模型（每層只依賴下一層）

```text
┌──────────────────────────────────────────────────────────────┐
│ L6 介面層   交易員終端 / 訊號卡 / 每日簡報 / 手機推播          │
├──────────────────────────────────────────────────────────────┤
│ L5 執行層   訂單意圖 → 券商 API / 影子帳本 / 成交回報對帳       │
├──────────────────────────────────────────────────────────────┤
│ L4 風控層   ★獨立閘門★ 部位大小、限額、相關性、熔斷、kill switch │
├──────────────────────────────────────────────────────────────┤
│ L3 決策層   訊號融合 → 組合建議（多模型投票 + meta-labeling）   │
├──────────────────────────────────────────────────────────────┤
│ L2 Agent 層 掃描 / 統計 / 情緒 / 事件 / 異常 / 敘事 Agent       │
├──────────────────────────────────────────────────────────────┤
│ L1 特徵層   point-in-time 特徵倉（feature store），版本化       │
├──────────────────────────────────────────────────────────────┤
│ L0 資料層   行情、基本面、資金流、新聞、社群、總經、另類資料     │
└──────────────────────────────────────────────────────────────┘
```

**單向規則**：L2 的 Agent 永遠不能直接讀 L0 的原始 API，必須經過 L1 的特徵倉。
理由是回測與即時必須走同一條路徑，否則 training-serving skew 會讓你在真錢上
才發現訊號長得不一樣。

## 2. 事件驅動骨幹

所有跨層溝通走**訊息匯流排**，不用直接函式呼叫，也不用互相 query 資料庫。

```text
market.tick.{venue}.{symbol}      行情快照（節流後）
market.bar.{freq}.{symbol}        1m / 5m / 1d K 棒（收線才發）
feature.updated.{set}.{symbol}    特徵重算完成
news.raw.{source}                 原始新聞／公告
news.enriched                     Agent 抽取實體與事件類型後
sentiment.scored.{symbol}         情緒分數更新
anomaly.detected.{type}           統計異常
signal.proposed                   Agent 提出的候選訊號
signal.confirmed                  決策層融合後的訊號
risk.approved / risk.rejected     風控裁決（含理由）
order.intent / order.ack / order.fill
system.health.{component}         心跳與延遲指標
```

三個設計要點：

- **at-least-once 傳遞 + 冪等消費**：每則訊息帶 `event_id`，消費端用它去重。
  重複的訊號絕不能變成重複的訂單（呼應檢核清單「用戶連點兩次不會被扣兩次錢」）。
- **event sourcing**：所有訊息落地成 append-only 的 log（Parquet 或 Kafka
  compacted topic）。任何一天的決策都能用當天的 log 完整重演。
- **背壓**：行情 tick 在來源端就節流（例如每檔每秒最多 1 筆快照），避免下游
  Agent 被淹沒。真正的高頻不是這套系統的目標。

## 3. Point-in-time 資料模型（最關鍵的一塊）

每一筆事實都有雙時間戳：

| 欄位 | 意義 |
| --- | --- |
| `event_time` | 事件本身發生的時間（財報期末、成交時間、新聞發布時間） |
| `ingested_at` | 系統實際拿到這筆資料的時間 |
| `revision` | 同一事件的第 n 次修訂，永不覆寫舊版 |
| `source_id` | 來源與擷取任務 ID，可回溯 |

回測與即時共用同一個查詢介面：

```python
fs.get(symbols, features, as_of=ts)   # 只回傳 ingested_at <= ts 的最新 revision
```

這條規則自動擋掉：

- **Look-ahead bias**：財報 3/31 期末但 5/15 才公布，回測在 4/1 讀不到它。
- **Survivorship bias**：universe 也是 point-in-time 的表，下市股票留在歷史中。
- **Restatement bias**：財報重編是 revision 2，回測讀到的是當時看到的 revision 1。

現有 repo 已經有這個雛形：`src/sector_rotation/strategy.py` 的
「一期訊號位移」（ranking 在期末算、下一期才使用）就是同一個思想的簡化版；
`data/databases/tw/*.parquet` 則是本地快取的雛形。差別是要把「位移」升級成
「as_of 查詢」，因為新聞與資金流的延遲不是固定一期。

## 4. 時間與時區

- 系統內部一律 **UTC 儲存**，顯示層才轉當地時區。
- 每個市場定義 `session_calendar`：開盤、收盤、盤前盤後、休市日、半日市。
- 「24 小時掃描」不代表 24 小時交易。實際運作是**跟著地球跑的班表**：
  亞洲時段（TW/JP/HK）→ 歐洲 → 美國 → 加密貨幣與期貨全天。
  每個時段有各自的 Agent 排程與資料來源優先序。
- 跨市場比較（例如台股 vs 美股 ADR）必須對齊到**共同的可交易時點**，
  不能拿不同收盤時間的價格直接算相關係數。

## 5. 執行環境拓撲

```text
                      ┌──────────────┐
   資料來源 ──────────►│ Ingestors    │ 每個來源一個獨立 worker
   (行情/新聞/公告)     │ (無狀態)      │ 失敗自動重試 + 死信佇列
                      └──────┬───────┘
                             ▼
                      ┌──────────────┐      ┌────────────────┐
                      │ Message Bus  │◄────►│ Event Log (S3) │
                      └──────┬───────┘      └────────────────┘
                             ▼
        ┌────────────┬───────────────┬──────────────┐
        ▼            ▼               ▼              ▼
   Feature Store  Agent Pool     Risk Engine    Observability
   (時序 DB)      (可水平擴充)    (單一實例+備援) (metrics/log/trace)
        │            │               │
        └────────────┴───────┬───────┘
                             ▼
                   Decision & Execution
                             ▼
                     Trader Console (L6)
```

- **Ingestor 無狀態**：可任意重啟；進度存在 checkpoint 表。
- **Agent Pool 可水平擴充**：每個 Agent 是一個消費者群組，按 symbol hash 分片。
- **Risk Engine 刻意不擴充**：單一權威實例（加 standby），因為部位限額需要
  全域一致視角。分散式風控會出現「兩個實例各自放行一半」的災難。
- **Observability 是一等公民**：沒有 metrics 的元件不准上線。

## 6. 三種運行模式（同一份程式碼）

| 模式 | 資料來源 | 執行 | 用途 |
| --- | --- | --- | --- |
| `backtest` | 歷史 event log 回放 | 模擬撮合 | 研究、參數搜尋 |
| `paper` | 即時資料 | 影子帳本，不送券商 | 上線前驗證、日常對照組 |
| `live` | 即時資料 | 券商 API | 真錢 |

**同一份程式碼**是重點。模式只由設定注入，若 `backtest` 與 `live` 走不同分支，
那條分支就是未來所有 bug 的溫床。paper 模式必須**永遠開著**，即使已經上 live，
用來即時偵測「模型漂移」與「實際成交 vs 理論成交」的落差。

## 7. 失效與降級

系統要能在部分壞掉時**繼續安全運作**，而不是全有或全無：

| 狀況 | 降級行為 |
| --- | --- |
| 新聞來源斷線 > 5 分鐘 | 情緒特徵標記為 `stale`，依賴它的訊號信心分數打折，不停機 |
| 行情延遲 > 3 秒 | 停止產生新訊號，既有部位轉為「只出不進」 |
| 特徵倉寫入失敗 | Agent 暫停，訊息留在 bus，恢復後補算 |
| LLM API 超時／限流 | 退回規則式分類器（保底路徑），並記錄降級事件 |
| Risk Engine 無回應 | **全面停止下單**（fail-closed，絕不 fail-open） |
| 券商 API 拒單率 > 20% | 熔斷，人工介入 |

原則：**資料層 fail-open（標記品質後繼續），交易層 fail-closed（停）**。

## 8. 回放與稽核

出事時要能在 10 分鐘內回答「為什麼下這一單」。做法：

1. 每個訊號帶 `decision_id`，串起它引用的所有 `event_id`、特徵版本、
   模型版本、風控裁決紀錄。
2. `replay --decision-id X` 用當時的 as_of 快照重跑整條鏈路，
   輸出應與當時完全一致（不一致本身就是嚴重 bug 警訊）。
3. 所有模型二進位檔與設定檔以內容雜湊命名，不可變。
