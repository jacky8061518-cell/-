# 02 Agent 分工與編排

## 1. 分工哲學

不要做「一個超級 Agent 什麼都問 LLM」。那樣不可測、不可回放、成本失控、而且
LLM 會在數字上犯低級錯誤。正確的切法是**依「輸入型態 × 時間尺度」切**，
每個 Agent 職責單一、輸入輸出用 JSON Schema 鎖死、可獨立測試與重跑。

三類 Agent，用不用 LLM 界線分明：

| 類型 | 用 LLM？ | 例子 |
| --- | --- | --- |
| **確定性 Agent** | 否 | 統計異常、動能排名、資金流、相關性、波動率 |
| **語意 Agent** | 是 | 新聞事件抽取、財報電話會議語氣、社群情緒、敘事聚類 |
| **推理 Agent** | 是（受限） | 跨來源交叉驗證、矛盾偵測、產生人話理由 |

**鐵律：LLM 不做算術。** 所有數值由確定性 Agent 算好，LLM 只負責讀懂文字、
分類、抽取結構、寫理由。要求 LLM 算 z-score 或報酬率，就是在買一張彩券。

## 2. Agent 名冊

### A. 市場掃描 Agent（Scanner）— 確定性
- **輸入**：`market.bar.*`
- **頻率**：每根 K 棒收線
- **職責**：維護每檔標的的滾動統計（見 [03](03-quant-models.md)），
  計算報酬、波動、成交量比、跳空、與大盤／同業的相對強弱。
- **輸出**：`feature.updated`
- **規模考量**：以 symbol hash 分片；5000 檔 × 每分鐘，單機 Python 足夠，
  但特徵計算要向量化（pandas/polars），不要逐檔迴圈。

### B. 統計異常 Agent（Anomaly）— 確定性
- **職責**：偵測「這個數字有多不尋常」。
  - 報酬 z-score 超過 ±2.5σ（用穩健估計，見 03）
  - 成交量 / 20 日均量 > 3
  - 波動率 regime 切換（HMM 或簡單的 ATR 比值）
  - 價量背離、與歷史 beta 的殘差異常
- **輸出**：`anomaly.detected`，帶 `severity` 與 `z_value`
- **重點**：異常 ≠ 訊號。異常只是「值得 LLM 花錢去看一眼」的觸發器。
  這是**成本控管的核心設計**：不是每檔股票每分鐘都餵給 LLM，
  而是統計層先篩出 0.5% 的候選，才觸發昂貴的語意分析。

### C. 新聞事件 Agent（News）— 語意
- **輸入**：`news.raw.*`（RSS、公開資訊觀測站、SEC EDGAR、交易所公告、財經媒體）
- **職責**（LLM 逐則處理，輸出結構化）：
  ```json
  {
    "event_id": "...",
    "entities": [{"symbol": "2330.TW", "role": "primary", "confidence": 0.94}],
    "event_type": "earnings_guidance_raise",
    "polarity": -1.0 ~ 1.0,
    "materiality": 0 ~ 1,
    "novelty": 0 ~ 1,
    "horizon": "intraday | days | weeks | structural",
    "evidence_span": "原文中支持判斷的句子",
    "source_tier": 1 ~ 3
  }
  ```
- **防幻覺三件套**：
  1. `evidence_span` 必須是原文的**逐字子字串**，程式端驗證，不符就丟棄重跑。
  2. `entities` 的 symbol 必須存在於 security master，否則丟棄。
  3. 同一則新聞若被兩個不同來源報導，交叉比對 `event_type` 是否一致；
     不一致則降低 confidence 並標記 `conflicting`。
- **去重**：新聞轉載嚴重。用 SimHash / embedding 相似度做 24 小時視窗去重，
  只有第一次出現才有 `novelty=1`。**重複報導不該被當成新資訊。**

### D. 情緒 Agent（Sentiment）— 語意
- **來源**：社群（有授權的前提下）、分析師報告摘要、法說會逐字稿、選擇權市場
  隱含的偏斜（這部分是確定性的）。
- **職責**：產生多維度情緒，而不是一個 -1~1 的黑箱數字：
  - `retail_sentiment`（散戶）、`institutional_tone`（機構）、
    `options_skew`（市場實際下注）、`analyst_revision_breadth`（調升家數比）
- **關鍵洞見**：情緒最有用的不是**水位**而是**變化率**與**分歧度**。
  「情緒從極度悲觀轉為中性」的訊號價值遠高於「情緒是正的」。
- **反指標處理**：極端散戶樂觀在多數研究中是反向指標。這件事必須由資料決定
  正負號，不能寫死在程式裡——交給 [03](03-quant-models.md) 的模型去學。

### E. 資金流 Agent（Flow）— 確定性
- **台股**：三大法人買賣超、融資融券、借券賣出、當沖比（現有
  `src/sector_rotation/fund_flow.py` 已實作骨架）
- **美股**：ETF 淨申贖、13F 變動（低頻）、暗池比例、大單分佈
- **職責**：判斷「錢實際往哪流」，這是最不容易被敘事污染的訊號源。
- 現有 `calculate_fund_flow_signals()` 的 `_flow_stage` / `_flow_reason`
  已經是「階段判斷 + 理由字串」的模式，可直接升級為本系統的 Flow Agent。

### F. 總經 / Regime Agent — 混合
- **職責**：判定當前市場處於哪種狀態，因為**同一個訊號在不同 regime 下的
  期望值完全不同**。
  - 維度：波動率高低、利率方向、信用利差、風險偏好（risk-on/off）、
    產業輪動位置（現有 `rrg.py` 的 RRG 象限正是此用途）
- **輸出**：`regime_label` + 各 regime 機率，供決策層當作條件變數。
- 這是整套系統中**最被低估**的一塊。多數策略失效不是因為模型爛，
  是因為 regime 換了而模型不知道。

### G. 交叉驗證 Agent（Corroborator）— 推理
- **職責**：在訊號發出前，檢查各路證據是否互相矛盾。
  - 新聞說利多，但法人在賣、選擇權偏空 → 標記 `divergence`，降低信心
  - 三個獨立來源指向同一結論 → 提高信心
- **輸出**：`corroboration_score` 與人話說明。
- 這是唯一允許 LLM 做「綜合判斷」的地方，且它**只能調整信心分數（有上下限
  夾擠），不能自己創造訊號**。

### H. 敘事 Agent（Narrative）— 語意
- **職責**：把當日所有事件聚類成「市場現在在講什麼故事」，
  例如「AI 資本支出疑慮」「降息預期後移」。
- **為什麼需要**：交易員不是需要 500 條新聞，是需要知道「今天市場的主軸是什麼，
  我的部位站在故事的哪一邊」。
- **輸出**：每日 3~7 個 narrative cluster，各附代表事件與受影響標的清單。

### I. 覆盤 Agent（Post-mortem）— 推理
- **頻率**：每日收盤後 + 每週
- **職責**：對照昨日發出的訊號與實際結果，產出：
  - hit rate、平均報酬、最大不利偏移（MAE）
  - 錯得最離譜的三個訊號的**歸因**（是資料錯？特徵漂移？regime 換了？）
  - 建議的參數調整（**只提建議，不自動改參數**——見下方）
- 這是整套系統的學習迴路，也是唯一能長期改善品質的機制。

## 3. 編排：不要用「Agent 自由聊天」

多 Agent 系統最常見的失敗是讓 Agent 互相對話直到「達成共識」。在交易場景這很糟：
不可預測的延遲、無法回放、成本爆炸、而且共識往往是同溫層放大。

改用 **有向無環圖（DAG）+ 黑板模式**：

```text
        每根 K 棒 / 每則新聞
                 │
        ┌────────┴────────┐
        ▼                 ▼
   Scanner(A)         News(C)
        │                 │
        ▼                 ▼
   Anomaly(B)        Sentiment(D)
        │                 │
        └────┬────────────┘
             ▼        ◄──── Flow(E)、Regime(F) 持續寫入黑板
      Corroborator(G)
             │
             ▼
      Decision Layer（L3，確定性融合）
             │
             ▼
      Risk Engine（L4）
```

- **黑板（Blackboard）**：一個以 symbol 為 key 的共享狀態存放區，
  各 Agent 只寫自己的欄位，決策層讀全部。避免 Agent 之間點對點耦合。
- **每個節點有 timeout 與 fallback**：Corroborator 3 秒沒回應就用預設
  `corroboration_score=0.5` 繼續走，不阻塞。
- **無迴圈**：若需要「再查一次」，做法是發出一個新事件觸發下一輪，
  而不是在同一輪內遞迴。這保證每一輪都會終止。

## 4. Agent 的自我改進邊界（重要）

「系統自己形成 trading models 而不靠人干預」是目標，但**不能是無限制的自動改參數**。
安全的做法是三層閘門：

| 層級 | 系統可自動做 | 需人工核准 |
| --- | --- | --- |
| L1 適應 | 調整既有模型的權重（在預設區間內）、隨 regime 切換已驗證的參數組 | — |
| L2 提案 | 產生新特徵、新模型候選，並自動跑完整驗證流程與 paper trading | 上線 |
| L3 結構 | — | 改變風控限額、新增資產類別、變更目標函數 |

系統可以自己搜尋、自己驗證、自己寫報告說「這個新模型在 walk-forward 上
Sharpe 1.4、在 paper 跑了 60 天」，但**按下上線按鈕的是人**。這既是風控，
也是法遵要求（多數轄區要求演算法交易有人為監督責任歸屬）。

## 5. Agent 的驗收（呼應檢核清單階段 5）

每個語意 Agent 都必須有 **evaluation set**：

- 人工標註 200~500 則歷史新聞／貼文的正確答案
- 每次改 prompt 或換模型，跑一次評測，記錄 precision / recall / 一致性
- 加上 **對抗樣本**：諷刺語氣、標題殺人、舊聞重發、同名公司混淆、
  數字單位陷阱（億 vs 百萬）
- **決不用「感覺變好了」驗收 prompt 改動**

確定性 Agent 則是標準單元測試 + property-based test
（例如：z-score 對輸入平移不變、對縮放尺度不變）。
現有 `tests/` 已有 `test_strategy.py`、`test_fund_flow.py` 的基礎可延伸。
