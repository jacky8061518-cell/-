# 08 技術選型與維運

呼應 Vibe Coder 檢核清單階段 4：**每個引入的套件都要答得出「它幫我省了什麼」，
答不出來的就移除。**

## 1. 目前實際使用的依賴

| 套件 | 它幫我省了什麼 | 有沒有替代 |
| --- | --- | --- |
| `pandas` | 時序對齊、rolling 視窗、groupby。手寫這些等於重寫半個 pandas | polars 更快，但 API 遷移成本高於目前的效益 |
| `numpy` | 向量化數值運算 | 無 |
| `streamlit` | 讓一個人在幾天內做出可互動的多頁交易台，不需要前後端分離 | 若要即時推播與手機版，才值得換 Next.js |
| `plotly` | 互動式圖表，滑鼠移上去能看數值 | matplotlib 不能互動，交易員會不滿意 |
| `yfinance` | 免費行情與新聞的取得 | 正式部署應換成有 SLA 的付費源 |
| `pyarrow`（經 pandas） | Parquet 讀寫，1.6 萬個交易日 × 2,333 檔只要幾百 ms | CSV 慢一個數量級 |

**刻意沒有引入的東西**，以及理由：

| 沒用 | 為什麼 |
| --- | --- |
| scipy | 只需要一個 inverse-erf，用 Winitzki 近似式（12 行）取代整包依賴 |
| scikit-learn | v1 的決策層是確定性規則，還沒到需要模型的階段。等做 meta-labeling 再引入 |
| 向量資料庫 | 敘事聚類目前用產業分群就夠。沒有實際痛點前不引入 |
| Kafka / Redis | 單機、日頻、一個使用者。訊息匯流排是 v2 的事 |
| LangChain 之類的 Agent 框架 | 我們的 Agent 是 DAG 不是自由對話，框架帶來的抽象層只會讓回放更難 |
| ORM / 資料庫伺服器 | append-only JSONL + Parquet 就滿足需求，且更容易在事故中直接 grep |

最後一項值得展開：**多 Agent 框架在交易場景通常是負資產**。
它們的核心賣點是「讓 Agent 互相對話直到達成共識」，而那正是
[02](02-agents.md) §3 說明必須避免的模式——不可預測的延遲、無法回放、
成本失控。我們要的是一個有 timeout 和 fallback 的 DAG，那用一般的 Python 寫就好。

## 2. LLM 使用與成本控管

### 成本閘門的實際設計

```text
2,333 檔標的
    ↓ 掃描（確定性，全市場，約 4 秒）
    ↓ 統計異常 + 資金流門檻
   568 個候選
    ↓ 要求跨來源交叉驗證
    75 個多來源候選
    ↓ 取前 30 檔（SentimentAgent.max_symbols）
    30 檔 × 5 則新聞 = 150 則 → 去重後約 100 則
    ↓ 只有這 100 則進 LLM
```

**每天約 100 次 LLM 呼叫，而不是 2,333 次。** 這不是最佳化，是架構決策：
統計層先做粗篩，是整套系統成本可控的唯一原因。

### 上線前必做的成本防護

- 每日 token 預算上限，超過就自動降級為詞典標註（fallback 路徑已實作）
- 雲端服務全部設定帳單警示，超過預算收到通知
- LLM 呼叫的 p50／p99 延遲監控；p99 超過 5 秒就檢討
- 快取：同一則新聞（content hash 相同）永不重複呼叫

## 3. 資安（檢核清單階段 6）

| 項目 | 現況 | 上線前要求 |
| --- | --- | --- |
| API key | 目前無需任何 key（本地資料庫） | 一律放環境變數或密鑰管理服務，前端與 git 紀錄裡搜不到任何一把 |
| 券商憑證 | 不適用（v1 不下單） | 獨立於應用程式的密鑰儲存；最小權限；只讀與交易權限分離 |
| `.streamlit/secrets.toml` | 已在 `.gitignore` | 維持 |
| 對外 API rate limit | 不適用（內部工具） | 若對外開放必須設，單一使用者刷不爆 token 額度 |
| 最壞情況 | 目前無 key 可外洩 | 接上券商後：key 外洩多快能撤銷？損失範圍多大？要先演練過 |

**現在就該想的一件事**：這套系統一旦接上券商 API，它的憑證就是可以直接
動錢的東西。在那之前，把密鑰管理的流程先建立好，不要等到要接的那天才想。

## 4. 部署

### 現況（單機）
```bash
pip install -e ".[dev]"
streamlit run app.py
```
本地資料庫已在 repo 中，**不需要外網即可完整運作**。

### 建議的正式部署
```text
資料更新    排程容器，每日執行 scripts/daily_update.py
流水線      排程容器，執行 run_desk() 並寫入 runs.jsonl
介面        Streamlit 容器，只讀 runs.jsonl 與資料庫
儲存        物件儲存（Parquet 與 JSONL）+ 每日備份
監控        流水線耗時、Agent 失敗率、資料新鮮度、LLM 成本
```

把「執行流水線」和「顯示結果」分成兩個容器有具體理由：
現在每次開頁面都重跑一次流水線（有 15 分鐘快取），
在正式環境應該是排程算好、介面只讀，這樣多人同時開頁面不會重複計算。

## 5. 效能現況

在本環境（單核心容器）實測：

| 階段 | 耗時 | 備註 |
| --- | --- | --- |
| 載入資料庫 | ~0.6s | 3,560 × 2,333 Parquet |
| Scanner（全市場特徵） | ~3.9s | 向量化後；逐欄 apply 版本要 7.4s |
| Regime | ~0.5s | |
| Anomaly | ~0.6s | 市場中性化後 |
| Flow | ~2.1s | |
| Sentiment | <0.1s | 未接新聞來源時 |
| Corroborator + Narrative | <0.1s | |
| **全流水線** | **~2.5-8.5s** | 依 universe 大小 |

955 檔的常用設定約 2.5 秒。這對日頻系統綽綽有餘；
若要做到分鐘級，Scanner 需要改成增量計算而非每次全量重算。
