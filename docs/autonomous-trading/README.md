# 自主式多 Agent 市場情報與訊號系統 — 設計總集

給**交易員**使用的系統設計文件。目標不是「AI 自動下單賺錢」，而是：

> 讓一群分工明確的 Agent 24 小時掃描市場，把價格、統計分佈、資金流、情緒與新聞
> 壓縮成**少數幾條有信心分數、有理由、有風險預算的訊號**，交易員只做「執行與否決」。

## 為什麼先定架構

自動交易系統壞掉的方式九成不是模型不準，而是：

- 用了未來資料（look-ahead / survivorship）自己騙自己；
- 資料延遲、缺漏沒被偵測，訊號建立在髒資料上；
- LLM 幻覺出一個不存在的事件，下游照單全收；
- 風控只寫在策略裡，模型一改就失效；
- 出事時沒有日誌可以回溯「誰、什麼時候、依據什麼、做了什麼」。

以上五件事**全部是架構問題，不是模型問題**。所以底層先定：
單向資料流、point-in-time 資料庫、事件溯源、風控獨立於策略、全鏈路可回放。

## 六條不可妥協的原則

1. **Point-in-time 至上**：每一筆資料都存「事件時間」與「入庫時間」兩個時間戳。
   任何回測只能讀取 `ingested_at <= 決策時間` 的資料。財報重編、成分股調整、
   新聞更正，都必須是新版本而不是覆寫。
2. **Agent 不直接下單**：Agent 產出的是**證據與建議**，只有 Risk Engine 有權
   把建議轉成訂單意圖，只有 Execution 有權送出。
3. **LLM 只做語意工作**：解析、分類、摘要、抽取實體、標記事件。
   任何涉及金額、部位、機率、閾值的計算一律走確定性程式碼（呼應檢核清單階段 3：
   「涉及金額、權限、庫存的運算一律放後端」——這裡是「一律放確定性層」）。
4. **每條訊號都要能回答三個問題**：依據哪些證據？信心多少？錯了會賠多少？
   答不出來的訊號不發出。
5. **風控是外部閘門**：策略永遠不能自己放寬自己的限額。風控參數獨立部署、
   獨立變更審核，且有一鍵 kill switch。
6. **先做 paper trading 六個月**：任何模型上真錢前，必須有完整的
   影子交易紀錄（含滑價與成本），並通過 [04](04-risk-control.md) 的上線檢查表。

## 與 Vibe Coder 自檢清單的對照

| 階段 | 在本系統的對應 |
| --- | --- |
| 1 需求驗證 | 最小可驗證版本＝**單一市場、單一資產類別、只發訊號不下單**；驗證標準＝交易員採用率與訊號後 5 日 hit rate |
| 2 前端體驗 | [05](05-signals-alerts.md) 的訊號卡／警示分級／每日簡報，桌機為主、手機推播為輔 |
| 3 後端邏輯 | [01](01-architecture.md)＋[06](06-data-contracts.md)：所有數值運算在後端、資料契約明確、可回放 |
| 4 技術選型 | [08](08-tech-stack.md)：每個套件都要答得出「它幫我省了什麼」 |
| 5 AI 協作 | [02](02-agents.md)：Agent 產出一律進 evaluation set，不靠感覺驗收 |
| 6 資安與成本 | [08](08-tech-stack.md) 的金鑰管理、rate limit、LLM token 預算與告警 |
| 7 金流 | 若對外訂閱制才需要；本系統 v1 為內部工具，暫不涉及 |
| 8 商業定位 | 內部工具：以「交易員省下的研究時數」與「訊號品質」衡量，非營收 |

## 合規與免責

本文件描述的是**研究與決策支援系統**。實際部署前必須確認：所在轄區的自動化
交易申報義務、經紀商 API 條款、資料供應商的再散布限制、以及公司內控的
交易前風控要求。系統不保證獲利；任何模型都可能在市場結構改變時失效。
