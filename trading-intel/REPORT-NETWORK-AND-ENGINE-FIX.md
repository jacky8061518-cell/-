## 一、網路開通後的實測結果：三種情況，不是「開了就全通」

環境的 Network access 從 Trusted 改為 Full 之後重新實測：

| 來源 | 結果 |
|---|---|
| 證交所 `openapi.twse.com.tw`、`www.twse.com.tw` | ❌ 仍被擋——但**不是我們的網路政策**擋的 |
| 櫃買中心 `www.tpex.org.tw` | ✅ 正常 |
| Yahoo Finance `query1.finance.yahoo.com` | ✅ 正常，含美股 AAPL 一併驗證過 |

**證交所被擋的原因確認過了**：對任意 API 路徑發請求，HTTP 狀態碼是 200，
但內容是 TWSE 自己的資安警示頁（「因為安全性考量，您所執行的頁面無法
呈現」）；裸網域首頁請求正常。這是 TWSE 自己的 WAF 對雲端機房 IP 段的
封鎖，路徑層級的規則，與我們的網路政策或請求內容無關。這不是能繞過、
也不是該繞過的東西——執行環境的說明文件本身的態度也是如此
（「不要重試或繞道，回報被擋的主機」）。

詳細診斷過程與決策記在 `docs/ADR/0007-yahoo-finance-source.md`。

## 三、用真實資料驗證基準策略時，抓到兩個回測引擎的真實 bug

這是本次最重要的發現。過程記在原始碼註解與新的 ADR 裡，這裡摘要：

**現象**：用五檔台股權值股（2330、2317、2454、2412、1301）兩年真實資料
跑「買進持有」策略，理論上全程只應該建倉一次、之後不再交易。實測跑出
**2420 筆成交**。

**根因**：回測引擎每天都用「當天的權益與價格」重新換算一次目標股數，
即使策略回傳的目標權重跟昨天完全一樣。權重沒變，但價格變了，換算出的
股數就跟著變，於是被迫產生交易——這是「每日再平衡到固定權重」，
不是「買進持有」。這個 bug 用合成資料測不出來，因為早期的合成測試用的
價格序列波動不夠真實、不足以持續觸發這個誤差。

**修正經過兩輪**：
- 第一輪嘗試在策略層修（讓 `BuyAndHold` 記住參考價、用價格漂移推導
  權重），成交筆數只從 2425 降到 2420，幾乎沒用。
- 診斷後發現：策略永遠不可能知道「明天」的真正成交價（決策看昨天、
  成交在今天，這正是防前視偏誤的設計），所以在策略層算不出正確答案。
- 第二輪修在引擎層：`_rebalance` 現在只對**目標權重真的改變**的標的
  重新換算股數，權重不變的標的直接跳過，任其隨價格自然漂移。

**修正後**：五檔股票兩年，成交筆數 **5 筆**（一檔一次），回測報酬與
手算報酬**位元層級吻合**（`pytest.approx(rel=1e-9)`）。`BuyAndHold` 的
策略程式碼也因此變回最初的簡單版本——問題原本就不在策略這層。

## 四、這件事的意義

如果沒有用真實資料測試，這個 bug 極可能一路帶到 Phase 4／Phase 5：
訊號融合、風控、儀表板全部建立在一個會把交易成本無故放大的回測引擎上，
而所有數字看起來都「正常」——2420 筆成交不會讓程式崩潰，只會讓所有
策略的回測績效系統性地偏低（成本被高估）。這正是 SPEC 第 12 節警告的
那種失敗模式：「投入時間應該七成在資料與驗證，三成在模型」。

需要換一個不在雲端機房 IP 段的執行位置，或等 TWSE 自己解除限制，

反推）或 `LEGACY`（繼承既有已調整價）兩種較低信心的來源。
