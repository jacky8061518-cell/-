# Phase 2 驗收報告：特徵層與回測引擎

規模：`src/` 4423 行、`tests/` 4628 行、**446 個測試通過**（10 個因缺 Redis 或
資料檔而跳過），`make check` 全綠。

SPEC 標註這一階段「品質決定整個系統的可信度，請優先正確性而非速度」，
因此本報告的重點放在**測試抓到的三個實質錯誤**。

---

## 驗收條件

| # | SPEC 第 11 節 Phase 2 驗收條件 | 結果 |
|---|---|---|
| 1 | 構造明顯用到未來資訊的特徵，回測引擎必須偵測並報錯 | ✅ 拋 `LookaheadError` |
| 2 | 對已知答案的合成資料，回測損益與手算結果誤差在浮點誤差內 | ✅ 相對誤差 < 1e-9 |
| 3 | 三個基準策略的績效數字落在文獻合理範圍 | ⚠️ 見下方說明 |
| 4 | 同一策略跑兩次，結果位元層級相同 | ✅ 逐日權益與成本完全相同 |

### 1. 前視偏誤被偵測

引擎的設計是**讓前視在結構上不可能發生**，而不是事後檢查。策略在時間 t 收到的
`MarketView` 只含 t 以前的資料——想看未來也拿不到。

三道測試：策略主動宣告要看明天 → 拋 `LookaheadError`；策略試圖翻找未來 bar →
翻不到；`MarketView` 在任何日期都只回傳該日以前的資料。

每個交易日的順序固定為：用**昨天收盤為止**的資料決策 → 以**今天**收盤價成交。
這個間隔寫死在引擎裡，策略無法用今天的收盤價決定今天要買什麼。

### 2. 手算比對

價格 100 → 105 → 110，零成本全額持有，初始一千元。第 1 天不交易（沒有「昨天」），
第 2 天以 105 建倉，第 3 天 110 收盤。期望 `1000 × 110/105`，實得相對誤差 < 1e-9。

權益全程以 `Decimal` 計算，不是浮點數。

### 3. 基準策略 ⚠️

三個都實作了並通過行為測試：買進持有、12-1 動量、三大法人買超排序。

**但無法用真實資料驗證績效是否落在文獻範圍**，因為：既有的十四年資料有存活者
偏誤（Phase 1 已量化，見 ADR 0005），拿它跑選股策略會得到虛高的績效，
那個數字沒有參考價值。網路被擋，也抓不到乾淨資料。

我沒有拿有偏誤的資料跑一個好看的數字充當驗收。這一條**在資料問題解決前無法完成**。

已完成的是行為驗證：買進持有的報酬確實追蹤標的本身；12-1 動量在全部下跌時
空手而非硬選最不差的；動量的「跳過最近一個月」機制確實避開短期反轉；
三大法人策略會自行過濾未來資料（外部訊號源不受引擎保護）。

### 4. 可重現

同一策略跑兩次，逐日權益、成本、成交紀錄完全相同。整段回測包在
`backtest_mode` 內——時鐘凍結、網路切斷，測試證實策略偷連網會被當場擋下。

## 測試抓到的三個實質錯誤

這一節是本報告的重點。三個錯誤都不會報錯，都會產生看起來正常的數字。

### 錯誤一：回測引擎的現金會計重複計入漲幅

原本用「權益減去部位成本」反推現金。但權益是**市值**、部位成本是**建倉價**，
兩者尺度不同，導致每天重複計入一次已實現漲幅。

十天的買進持有測試中，正確答案是 1079.2，錯誤實作給出 1089.1——**高估 0.9%**。
在一年的回測裡這會累積成巨大的虛假報酬。

修正：現金與部位分開記帳，買賣直接增減現金，成本由現金支付。

### 錯誤二：Sharpe 對常數序列算出 9×10¹⁶

`[0.01] * 100` 的樣本標準差因浮點誤差是 `1.7e-18` 而非 0，於是
Sharpe = 0.01 / 1.7e-18 × √252 ≈ **9×10¹⁶**。

這個數字不會報錯，而且會在任何策略排序中排第一。會踩到它的情況包括：
只持有現金的策略、資料壞掉導致價格不變的標的。

修正：改用相對門檻判斷「實質無波動」，而非 `std == 0`。

### 錯誤三：Deflated Sharpe 的尺度錯誤

原本 `variance_of_trial_sharpes` 給了預設值 1.0，而觀測 Sharpe 常被當成年化值傳入。
兩者尺度不一致，算出的機率沒有意義——測試發現「觀測數增加反而信心下降」，
與統計直覺相反。

修正：該參數改為**必填**（它是「你試過的那些策略的 Sharpe 變異數」，只有呼叫端
知道，給預設值等於替使用者猜一個關鍵參數），並在文件明確要求傳入非年化值。

### 另外兩個較小的問題

- **`test_stationarity` 這個函式名會被 pytest 當成測試收集。** 改名為
  `check_stationarity`。
- **半衰期估計用普通 t 檢定會放行隨機漫步。** 在單位根附近，OLS 的 t 統計量
  不服從標準 t 分布而是 Dickey-Fuller 分布。實測一條 2000 點的隨機漫步，
  普通 t 檢定讓它「顯著」通過並估出 163 期的半衰期——完全虛假。
  改為先過 ADF 才估計，這也與 SPEC 5.1 的原文一致（「對**通過的**序列估計」）。

## 交付內容

| 模組 | 行數 | 說明 |
|---|---|---|
| `features/statistics.py` | 300 | ADF/KPSS 合議、OU 半衰期、EWMA、Yang-Zhang、winsorize |
| `features/registry.py` | 200 | 特徵註冊表（版本、相依欄位、值域把關）、橫斷面中性化 |
| `backtest/engine.py` | 330 | 逐事件回測引擎，內建前視偵測與現金記帳 |
| `backtest/costs.py` | 100 | 台股成本模型，證交稅只在賣出時課 |
| `backtest/validation.py` | 340 | purged walk-forward、CPCV、DSR、PBO、容量曲線 |
| `backtest/baselines.py` | 140 | 三個基準策略 |

**統計模組的關鍵設計**：未通過定態檢定的序列，均值回歸類特徵一律回傳 NaN
而非硬算。回傳 NaN 讓下游少一個訊號；硬算讓下游多一個**錯誤**訊號。
兩者代價不對稱。

**驗證協定的核心問題只有一個：你試了幾次？** 試一百組參數總有幾組看起來好，
那不是因為有效，是因為一百個隨機數裡本來就有最大值。四道防線分別處理標籤重疊
洩漏、單一曲線的誤導、多重檢定、以及過度配適機率。

## 設定檔的修正與填值

依指示填入風控假設值，每一條都附推理，見 `configs/base.yaml`。

**同時修正一個先前的錯誤**：手續費原填 `1.425`，但台股手續費是 0.1425%
＝ **14.25** 個基點，少了十倍。這正是 SPEC 第 12 節點名的失敗模式
（「交易成本低估，尤其台股證交稅對高換手策略是致命的」）。已加測試防止再犯。

法定稅率（證交稅 0.3%、當沖 0.15%）不是假設值，維持原樣。

覆蓋率門檻也從「靠人記得」改為自動執行：`make coverage-gates` 會逐一檢查
CLAUDE.md 規定的三個目錄，不足 90% 直接失敗。

你提到可以改用 Yahoo Finance 或 CMoney。我實測了：

| 來源 | 結果 |
|---|---|
| Yahoo Finance API | 403 拒絕 |
| CMoney | 403 拒絕 |

| 櫃買中心 | 403 拒絕 |

這台機器的出口有白名單，只放行 GitHub 與 Python 套件庫等少數幾個。
**所有金融網站一律拒絕，不分哪一家。** 問題不在資料來源，在執行環境的網路政策。

這不影響 Phase 2——回測本來就規定禁止連網。它影響的是「用真實資料驗證基準策略」
這一條驗收。
