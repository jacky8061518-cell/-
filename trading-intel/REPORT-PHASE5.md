## 1. 訊號卡：失效條件與反方論點是型別層級的要求

`surface/signal_card.py`。SPEC 8.1 說失效條件是「最重要」的欄位，
Phase 0 已經用 `min_length=10` 把這件事釘進 `Signal` 型別；這裡再加一層：
**沒有 `RedTeamAgent` 報告不得產卡**，`build_signal_card` 直接拒絕。

一個容易漏掉的細節：`NOT_APPLICABLE` 的檢查項不計入反方論點——否則八項
清單裡五項寫「不適用」也會顯示成五條反方意見，稀釋掉真正該注意的那幾條。

## 2. 分級告警：抗疲勞跟分級本身一樣重要

`surface/alerts.py`。SPEC 開門見山「告警疲勞是這類系統最常見的死因」，
所以測試的重心放在三道防線而非分級邏輯本身：

- **去重**：內容指紋完全相同、或相似度超過門檻的，一律擋下；
- **速率上限**：超過每小時上限，`AlertRouter.submit` 回傳 `Digest` 而非
  逐則 `Alert`——呼叫端拿到的型別本身就會提醒你該怎麼處理；
- **novelty 檢查**：24 小時內講過的內容降級，時窗一過才重新算新鮮。

`Alert` 建構時直接檢查 `action` 欄位不得為空——「所以呢」那句話是
建構函式層級的要求，不是文件裡的建議，寫不出來就建不出這個物件。

P0 之下沒有更嚴重的層級了，因此 P0 一律跳過全部節流機制直接送出。

## 3. 盤前晨報與盤後歸因

`surface/morning_brief.py` 組裝，`surface/attribution.py` 計算。

歸因模組刻意**不用 LLM**（SPEC 4.2 原本規劃為 agent，這裡改回純程式碼），
理由跟 regime 分類一樣：拆解損益是算術，不是語意任務。核心不變條件寫在
`AttributionResult.__post_init__`：alpha + beta + 風格 + 成本 + 時機
必須恆等於總報酬，對不上就直接拋錯——歸因模組本身寫錯了不該悄悄放過。

晨報模組本身沒有任何計算邏輯，純粹組裝 regime、風控、訊號卡已經算好的
東西——這個分工的理由是 SPEC 1「LLM 不碰數字」精神的延伸：連組裝報告的
程式碼也不該重算數字，一律引用上游算好的結果。

## 4. 風險儀表板：看「離觸發還有多遠」，不是限額本身

`surface/dashboard.py`。核心設計是 `LimitUsage.usage_ratio`——交易員需要
知道的是使用率而非限額數字（那在 configs 裡）。使用率超過八成標記
`is_near_limit`，讓警戒訊號在真正觸發之前就顯示出來。

## 5. 紙上交易模式

`surface/paper_trading.py`。SPEC 講得很精準：「完整走完決策路徑但不
下單」。這裡的設計決定是**不接 `backtest_mode`**——那個 context manager
是為回測設計的（凍結時鐘、切斷網路），紙上交易要反過來：真實時鐘、
可以連網，只在「送出委託」這一步停手。

`PaperOrder` 沒有任何看起來像下單確認的欄位（`broker_order_id`、
`submitted` 皆不存在），這件事只能靠設計保證，測試裡驗證了這一點作為
提醒——真正的保證來自程式碼裡壓根不存在下單相關的 import 或呼叫。

`weekly_summary` 直接對應 SPEC「每週檢視」的三項：決策數（含被否決的）、
agent 成本、告警訊噪比。

## 沒做到的事：紙上交易三個月

SPEC 第 5 點的完整要求是：「紙上交易模式，完整走完決策路徑但不下單，
每日記錄」，且「紙上交易至少執行三個月，期間每週檢視」。

**我把「紙上交易的機制」做完了，但無法真的執行三個月。** 這不是我漏做，
是這件事在本質上做不到：

- 這個執行環境沒有能跨三個月存活的常駐行程——每個 session 都是有限
  存續期的容器，程式跑完就結束了。
- 就算能常駐，「紙上交易」的定義本身就是要用**真實時間**走過三個月的
  交易日，不是用模擬時鐘在幾秒內跑完——那樣就變回回測，不是紙上交易，
  SPEC 8.1 對這兩者的區分正是本模組設計時強調的重點。
- 三個月的紙上交易也需要 Phase 3 的 LLM agent 真的每天跑、真的花錢，
  而不是用 `ScriptedClient` 離線測試。

**我做的是把「執行三個月紙上交易」需要的全部零件蓋好並測過**：決策路徑
的每一步都有對應模組（訊號 → 風控 → 組合 → 告警 → 記錄），
`PaperTradingBook` 可以逐日累積、逐週摘要。真正的三個月執行，
需要在一個能長期運作的環境裡，每個交易日跑一次完整流程並持續記錄——
那是部署層面的工作，不是這個 session 能完成的程式碼任務。
