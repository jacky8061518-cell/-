# 事件分類法 v1（待核定）

SPEC 第 11 節 Phase 3 要求：「事件分類法固定在 30 類以內，**先產出分類法文件給我審核**」。

以下共 **26 類**，留 4 類餘裕給日後新增而不必立刻改版。

## 設計原則

**分類法要能被回測。** 每一類都必須對應一個可檢驗的價格反應假設。
「公司有好消息」不是一類，因為它無法被檢驗；「上調財測」是一類，
因為可以問「上調財測後 5 日的超額報酬分布長什麼樣」。

**寧可粗不要細。** 30 類已經偏多。分得太細會讓每類的樣本數不足以做統計，
而樣本不足的分類等於沒有分類。

**互斥但不必窮盡。** 一則新聞只歸一類（取最主要的）。無法歸類的走 `OTHER`，
並在月度檢討時看 `OTHER` 的比例——比例持續偏高代表分類法需要修訂。

## 附帶欄位

`event_type` 只是分類。每則事件另外帶四個欄位，這些才是訊號的原料：

| 欄位 | 值域 | 說明 |
|---|---|---|
| `surprise_direction` | `POSITIVE` / `NEGATIVE` / `NEUTRAL` | 相對市場預期的方向，不是消息本身的好壞 |
| `magnitude_bucket` | `MINOR` / `MODERATE` / `MAJOR` | 刻意用三分類而非連續值，因為 LLM 不碰數字（SPEC 1） |
| `horizon` | `INTRADAY` / `DAYS` / `WEEKS` / `MONTHS` | 預期影響持續多久 |
| `novelty_score` | 0 到 1 | **由確定性程式碼計算**，非 LLM 輸出 |

**`novelty_score` 為什麼不給 LLM 算**：同一則消息被 50 家媒體轉載，
不等於情緒強度乘以 50（SPEC 4.2）。去重與新穎度是「這件事過去 30 天出現過嗎」
的檢索問題，有確定的答案，不該交給模型判斷。

## 待你核定

1. **26 類會不會太細或太粗？** 我的判斷是偏細一點點，
   但 D 與 E 兩組可能可以各併掉一類。
2. **`REVENUE_MONTHLY` 值得單獨一類嗎？** 台股每月 10 日前公布月營收，
   這是台股特有且高頻的事件，我認為值得，但它也可以併進 `EARNINGS_BEAT/MISS`。
3. **有沒有你在意但漏掉的事件類型？** 例如法說會的語氣轉變目前歸在
   `GUIDANCE_RAISE/CUT`，若你認為「語氣轉變但財測未變」值得單獨追蹤，
   那要新增一類。

分類法一旦上線就不該隨便改——改了之後舊訊號的分類與新訊號不可比，
歷史統計要重算。所以現在多花十分鐘討論是值得的。
