## 設計原則

**分類法要能被回測。** 每一類都必須對應一個可檢驗的價格反應假設。
「公司有好消息」不是一類，因為它無法被檢驗；「上調財測」是一類，
因為可以問「上調財測後 5 日的超額報酬分布長什麼樣」。

**寧可粗不要細。** 30 類已經偏多。分得太細會讓每類的樣本數不足以做統計，
而樣本不足的分類等於沒有分類。

**互斥但不必窮盡。** 一則新聞只歸一類（取最主要的）。無法歸類的走 `OTHER`，
並在月度檢討時看 `OTHER` 的比例——比例持續偏高代表分類法需要修訂。

## 附帶欄位

`event_type` 只是分類。每則事件另外帶四個欄位，這些才是訊號的原料：

| 欄位 | 值域 | 說明 |
|---|---|---|
| `surprise_direction` | `POSITIVE` / `NEGATIVE` / `NEUTRAL` | 相對市場預期的方向，不是消息本身的好壞 |
| `magnitude_bucket` | `MINOR` / `MODERATE` / `MAJOR` | 刻意用三分類而非連續值，因為 LLM 不碰數字（SPEC 1） |
| `horizon` | `INTRADAY` / `DAYS` / `WEEKS` / `MONTHS` | 預期影響持續多久 |
| `novelty_score` | 0 到 1 | **由確定性程式碼計算**，非 LLM 輸出 |

**`novelty_score` 為什麼不給 LLM 算**：同一則消息被 50 家媒體轉載，
不等於情緒強度乘以 50（SPEC 4.2）。去重與新穎度是「這件事過去 30 天出現過嗎」
的檢索問題，有確定的答案，不該交給模型判斷。

## 核定紀錄（Claude 代為決定，2026-09-11）

1. **26 類會不會太細或太粗？** 決定：**維持不變，不合併 D、E**。
   理由：合併容易、拆分難——一旦兩類被合併成一類，之後想再拆開，
   舊資料已經不可逆地混在一起，無法回頭補救。而目前的餘裕（27/30）
   還很充足，不急著現在就為了「感覺上比較精簡」而犧牲彈性。
   正確的做法是照文件本來訂的規則走：先上線觀察，之後看每一類的
   `OTHER` 佔比與樣本數，真的長期用不到、樣本稀少到無法統計的類別，
   再合併也不遲。
2. **`REVENUE_MONTHLY` 值得單獨一類嗎？** 決定：**維持獨立一類，不併入
   `EARNINGS_BEAT/MISS`**。理由：月營收是排程公布（每月固定時間、頻率遠高於
   季報），而 `EARNINGS_BEAT/MISS` 是財報公布時的「意外方向」判斷——
   兩者觸發時機與樣本頻率的性質不同，混在一起會讓「典型持有期」欄位
   失去意義（月營收與季報的價格反應窗口本來就不一樣長）。
3. **有沒有漏掉的事件類型？** 決定：**新增 `EARNINGS_CALL_TONE`**
   （法說會或公開發言語氣轉變，但財測數字本身未變），歸在 A 組第 6 類。
   理由：這是台股法說會文化中常見、但過去被迫塞進 `GUIDANCE_RAISE/CUT`
   的情況——語氣轉變早於財測正式調整，若都算同一類會讓「財測調整」
   這個類別的訊號被「語氣訊號」稀釋，兩者的確定性與典型持有期也不同。

**重要提醒**：以上是我依專案設計原則（可回測、寧粗勿細、互斥不窮盡）
做出的判斷，不是你本人核定的。分類法上線後，舊訊號的分類與新訊號
一旦類別有變動就不可比，歷史統計必須重算——如果你之後有空看過這份
文件、覺得哪裡不妥，請儘早提出，越晚改代價越高。
