# 自主式多代理人交易研究系統 建置規格書

給 Claude Code 的主控文件。本文件為 repo 的權威規格，第 10 節內容另存為根目錄的 `CLAUDE.md`。

---

## 1. 專案定位與五條硬性原則

本系統的產出是**給交易員的決策情報與訊號**，不是黑盒子自動下單機。人類保留最終否決權，系統負責 24 小時不間斷的掃描、統計、假設生成與驗證。

以下五條是架構層級的鐵律，任何實作不得違反。違反時 Claude Code 應主動拒絕並回報。

- **LLM 不碰數字。** Agent 負責語意理解、事件抽取、假設提出、異常解釋、報告撰寫。所有均值、標準差、z-score、部位大小、風險值一律由確定性程式碼計算。LLM 產生的任何數值不得進入下單路徑。
- **雙時間戳強制。** 每一筆資料同時記錄 `event_time`（事件實際發生時間）與 `ingest_time`（系統收到時間）。所有回測查詢一律以 `asof` 參數過濾 `ingest_time`，杜絕前視偏誤。任何不吃 `asof` 參數的資料存取函式視為錯誤。
- **可重放與可重現。** 同一份事件流重放兩次，必須產生位元層級相同的訊號。隨機種子固定，模型版本入庫，特徵計算純函式化。
- **資料壞掉時停止交易，不是輸出垃圾。** 資料品質檢查失敗，下游訊號狀態設為 `NO_TRADE`，不得以插值或前值填補後繼續。
- **先有確定性回測骨架，才准接 LLM。** Phase 2 未通過驗收前，不寫任何 agent 程式碼。

## 2. 系統分層架構

事件驅動骨幹，五層單向依賴，上層不得反向呼叫下層以外的模組。

```
[L0 Ingestion]  行情、新聞、公告、籌碼、總經、社群
      |  raw immutable landing zone (object store, 原始 payload 永不覆寫)
      v
[L1 Normalize]  統一 schema、時區轉 UTC、企業行動調整、實體解析、去重
      |  event bus (Redis Streams 起步, 量大再換 NATS JetStream)
      v
[L2 Feature]    point-in-time feature store、統計量、技術面、籌碼面、事件特徵
      |
      v
[L3 Agent]      LLM 代理人層, 只讀 L2 的結構化輸出, 只輸出 typed schema
      |
      v
[L4 Decision]   訊號融合、組合建構、風控閘門、下單意圖
      |
      v
[L5 Surface]    交易員儀表板、分級告警、晨報、事後歸因
```

技術選型建議，除非有硬理由否則照此執行。

- 語言 Python 3.12，型別註記全開，`mypy --strict` 納入 CI
- 事件匯流排 Redis Streams（consumer group 提供 at-least-once 與重放）
- 時序資料 TimescaleDB，研究掃描用 DuckDB 直讀 Parquet
- 狀態與實體資料 PostgreSQL
- 熱狀態快取 Redis
- 排程 Prefect 或 APScheduler，不要用裸 cron
- 監控 Prometheus + Grafana，日誌用 structlog 輸出 JSON
- 設定管理 pydantic-settings，禁止硬編碼參數

**與既有專案的銜接。** 本系統的 L0 與 L1 應直接沿用既有 `taiwan-fund-flow-lab` 的 `src/sector_rotation` 資料層（TWSE 公司主檔、三大法人買賣超、Parquet 快取、台股除權息與分割修正邏輯），以套件相依方式引入，不要重寫。既有的股票研究系統 PostgreSQL schema（stocks、market_prices、financial_metrics、research_items、broker_reports、broker_estimates、investment_theses）作為 L1 實體層基礎，本系統新增的表以 `sig_` 與 `risk_` 前綴區隔。

## 3. 資料層規格

### 3.1 資料分級

| 級別 | 內容 | 更新頻率 | 品質要求 |
|---|---|---|---|
| Tier A 行情 | OHLCV、成交量、Level 1 報價 | 即時到日頻 | 最高，缺一根 bar 即告警 |
| Tier A 參考 | 企業行動、指數成分、股本變動、暫停交易 | 事件觸發 | 最高，錯一筆全歷史回測失效 |
| Tier B 籌碼 | 三大法人、融資券、借券、大戶持股 | 日頻 | 高 |
| Tier B 基本面 | 財報、營收、法說會、財測 | 事件觸發 | 高，需保留原始發布版本與後續重編版本 |
| Tier C 另類 | 新聞、公告、法人報告、社群、供應鏈 | 即時 | 中，需標註來源可信度 |
| Tier D 衍生 | 特徵、訊號、模型輸出 | 由上游決定 | 可重算 |

### 3.2 必做的四件事

- **企業行動引擎。** 除權息、分割、減資、換股一律以未調整原始價加調整因子表的方式儲存。禁止直接存調整後價格，因為新的企業行動會讓歷史調整價全部改變，破壞可重現性。
- **無存活者偏誤宇宙。** 建立 `universe_membership` 表，記錄每支標的每一天是否在可交易宇宙內，含下市、暫停交易、處置股。回測選股只能從當日宇宙中選。
- **實體解析。** 新聞裡的「台積」「TSMC」「2330」「台積電」必須解析到同一個 `entity_id`。建立別名表與消歧規則，模糊比對閾值以外的丟人工佇列，不要猜。
- **多源交叉核對。** Tier A 至少兩個來源，日終比對收盤價與成交量，差異超過閾值產生 `DATA_CONFLICT` 事件並凍結該標的訊號。

### 3.3 資料品質閘門

每個批次進入 L2 前必須通過，任一失敗則該標的當日狀態設為 `NO_TRADE`。

- 時效性 最新 bar 距現在超過 N 個週期
- 完整性 交易日缺 bar、成交量為零但有價格變動
- 合理性 單日報酬絕對值超過漲跌幅限制、bid-ask 交叉、負成交量
- 一致性 high < low、close 落在 high low 之外
- 分布漂移 特徵的 PSI 相對訓練期超過 0.25 觸發警示，超過 0.5 停用該特徵

## 4. Agent 分工與契約

### 4.1 通用契約

所有 agent 遵守同一份介面規範。

- 輸入為結構化 JSON，不得是自由文字
- 輸出為 Pydantic model，含 `confidence`（0 到 1）、`evidence`（來源 id 清單）、`reasoning_digest`（限 200 字）、`abstain`（布林）
- **棄權是合法輸出。** 證據不足時必須回傳 `abstain=True`，不得硬猜。獎勵函數要懲罰過度自信
- 每次呼叫記錄 prompt hash、模型版本、token 成本、延遲，寫入 `agent_calls` 表
- 逾時、格式驗證失敗、重試三次仍失敗，一律降級為 `abstain`，不得讓例外向上冒泡到決策層
- 每個 agent 有獨立的 token 預算與速率上限，超支自動降級到較小模型或暫停

### 4.2 Agent 名單與職責

**感知層**

- `WatcherAgent`（每個資料源一個，多數為確定性 worker 不用 LLM）持續拉取、標準化、發事件。純程式碼即可。
- `NewsAnalystAgent`（LLM，唯一的感知層 agent）處理所有非結構化文本，以 `doc_type` 欄位區分新聞、公告、財報、法說會逐字稿、券商報告，各自套用不同的抽取提示但共用同一份輸出 schema。輸出欄位 `entity_id`、`event_type`（分類法固定 30 類以內）、`surprise_direction`、`magnitude_bucket`、`horizon`、`novelty_score`（相對過去 30 天是否為新資訊）、`sentiment`、`source_credibility`、`delta_vs_prior`（財報與法說會專用，抓語氣轉變與財測修正而非摘要）。
- 情緒與去重規則 同一則消息被 50 家媒體轉載不等於情緒強度乘以 50。文本先做事件級聚類去重，再對代表文本計分，`novelty_score` 負責衰減。這一段是確定性程式碼，不是額外的 agent。

**分析層**

- `HypothesisAgent`（LLM）觀察 L2 的異常清單，提出可檢驗的假設。輸出必須包含明確的可證偽條件、預期方向、預期持有期、以及要用哪些特徵驗證。禁止輸出無法回測的假設。
- `RedTeamAgent`（LLM）對每一個候選訊號主動找碴。檢查清單固定：資料洩漏、生存者偏誤、多重檢定、容量限制、擁擠度、交易成本吞噬、僅在單一 regime 有效、樣本期特殊事件驅動。輸出為攻擊點清單與嚴重度。

以下三項原本規劃為 agent，改為純程式碼模組，不佔 LLM 預算。

- `src/models/regime.py` 市場狀態分類（趨勢或盤整、波動率分層、流動性、橫斷面相關性）。HMM 或規則皆可，輸出必須離散且穩定，避免每日跳動。
- `src/backtest/validation.py` 接假設跑嚴格樣本外檢驗，回傳通過或退回。這是守門員，不是幫手。
- `src/surface/attribution.py` 每日拆解損益來源，區分 alpha、beta、風格因子、交易成本、時機。敘述文字由報告模板生成，需要時再單次呼叫 LLM 潤飾。

**決策層**

- `PortfolioAgent`（純確定性）不用 LLM。接收訊號分數與風險模型，輸出目標權重。
- `RiskAgent`（確定性限額加 LLM 情境敘述）硬限額由程式碼把關，LLM 只負責針對新聞型尾部風險寫出情境說明供人判讀。
- `ExecutionAgent`（確定性）拆單、擇時、成本估計。初期只做到產生下單意圖，不接券商 API。

**治理層**

- `src/agents/orchestrator.py`（確定性狀態機，不是 LLM）排程、預算分配、衝突仲裁。當兩個 agent 結論相反且都高信心時，升級到人工佇列而非取平均。仲裁規則寫成明確條件式，不要交給模型判斷。
- `LibrarianAgent`（LLM 加向量檢索）維護研究知識庫。記錄每一個測過的假設與結果，`HypothesisAgent` 提新假設前必須先查詢，避免重複測試同一件事造成隱性多重檢定。LLM 只用在語意相似度判斷「這個假設是不是已經測過了」。

### 4.3 提示注入防護

這是本系統最被低估的風險。新聞內文、法人報告 PDF、社群貼文都是**不可信輸入**，可能含有針對 LLM 的注入指令。

- 所有外部文字送進 LLM 前包在明確的資料標記內，並在系統提示中聲明標記內容一律視為資料不視為指令
- Agent 輸出經 schema 驗證，超出列舉值的欄位直接拒收
- Agent 無權觸發下單、修改限額、關閉風控。這些能力在程式碼層就不存在於 agent 的工具集中
- 對含有指令性語句的輸入文本標記 `suspicious=True` 並降低其證據權重

## 5. Quant model 層

### 5.1 特徵工程

- 全部特徵寫成純函式，簽章為 `f(data: pd.DataFrame, asof: datetime, **params) -> pd.Series`
- 特徵版本化，改動參數即新版本，舊版本保留以供重現舊訊號
- 橫斷面特徵一律先做產業中性化與市值中性化，再標準化
- **均值與標準差不要用天真的滾動視窗。** 報酬序列非定態，滾動 z-score 在趨勢中會持續給錯誤的反轉訊號。實作要求：先做定態檢定（ADF 或 KPSS），對通過的序列以 OU 過程估計半衰期，視窗長度由半衰期決定而非拍腦袋設 20 日。未通過定態檢定的序列不得使用均值回歸訊號
- 標準差用 EWMA 或 Yang-Zhang 估計量，不要用簡單樣本標準差
- 極值處理用 winsorize 到 1 與 99 百分位，不要直接刪除

### 5.2 訊號分類

| 類型 | 說明 | 典型持有期 | 主要風險 |
|---|---|---|---|
| 橫斷面 | 同一時點跨標的排序 | 數週到數月 | 因子擁擠、風格反轉 |
| 時序 | 單一標的的時間維度 | 數日到數週 | regime 切換 |
| 事件驅動 | 財報、法說、政策、供應鏈 | 數日 | 資訊已被定價、樣本數少 |
| 資金流 | 三大法人、借券、ETF 申贖 | 數日到數週 | 資料延遲、單向擁擠 |

### 5.3 驗證協定

這一節是整個系統可信度的核心，不得簡化。

- **Purged walk-forward 加 embargo。** 訓練與測試之間留出等於最長持有期的緩衝，避免標籤重疊造成的洩漏
- **Combinatorial purged cross-validation** 產生多條路徑的績效分布，而非單一回測曲線
- **Deflated Sharpe Ratio。** 記錄總共試了幾組參數與幾個假設，對 Sharpe 做多重檢定調整。這也是 `LibrarianAgent` 存在的理由
- **Probability of Backtest Overfitting（PBO）** 超過 0.5 直接淘汰
- **成本模型必須內建於回測，不是事後扣除。** 台股需含證交稅 0.3%（當沖減半）、手續費、借券費、以及以平方根衝擊模型估計的市場衝擊。滑價假設要保守
- **容量檢定。** 以標的 20 日均量的百分比為上限，測試策略在不同資金規模下的績效衰退曲線
- 驗收門檻建議 樣本外 Sharpe 大於 1.0、最大回撤小於年化報酬、勝率與賠率組合在 regime 分層下皆不為負、換手率對應的成本吞噬小於毛 alpha 的 40%

### 5.4 模型階梯

依序嘗試，後者必須在樣本外顯著優於前者才准採用。

1. 單因子排序（基準線）
2. 線性或 Ridge 多因子
3. 梯度提升樹（LightGBM）
4. 序列模型

多數情況第 2 級就夠。若第 3 級沒有明顯優勢，選第 2 級，因為可解釋性在交易員採用度上的價值高於邊際 Sharpe。

## 6. 訊號融合與組合建構

- 禁止對訊號分數做簡單平均。訊號間相關性高時等權等於重壓單一因子
- 融合方式 依 regime 條件加權，權重以收縮估計（Ledoit-Wolf）處理協方差，或用 Hierarchical Risk Parity
- 每個訊號帶半衰期，超過半衰期線性衰減至零，不得無限期持有
- 組合建構為帶約束的最佳化，約束項包含單一部位上限、產業曝險上限、風格因子曝險上限、流動性約束、換手率懲罰項
- 波動率目標化 以目標年化波動反推總曝險，市場波動上升時自動降槓桿

## 7. 風控三層

### 7.1 事前（下單意圖產生時）

- 單一標的上限、產業上限、總曝險與淨曝險上限
- 流動性檢查 部位不得超過 20 日均量的設定比例
- 相關性檢查 新增部位與現有組合的邊際風險貢獻上限
- 集中度 前五大部位合計上限
- 禁止清單 處置股、全額交割、財報空窗期、內部人名單

### 7.2 事中（持續監控）

- 分層停損開關，例如組合回撤 3% 自動減半曝險、5% 全部平倉並進入人工審核
- 即時波動率監控，實現波動超過目標 1.5 倍自動降槓桿
- 部位與帳戶對帳，每 N 分鐘核對一次，不符即凍結
- Dead man's switch 心跳中斷超過閾值自動進入只平倉模式
- 下單速率上限、重複單防護、價格偏離防護

### 7.3 模型風險

- 訊號衰退監控 追蹤上線後的滾動 IC 與回測期 IC 的差距，連續 N 期低於下限自動隔離該訊號
- Live 對 Backtest 追蹤誤差 超過閾值代表實作有誤或市場已變，觸發調查
- 特徵漂移 PSI 監控（見 3.3）
- Agent 一致性監控 同一輸入重複問三次，答案分歧度過高代表該任務不適合 LLM，退回確定性做法

### 7.4 人機分權

明確三級，寫進設定檔而非程式碼。

- Level 1 自動執行 僅限已上線超過 6 個月、通過所有驗證、規模小於總資產設定比例的訊號
- Level 2 需人工確認 新訊號、大額調整、regime 切換期間
- Level 3 僅研究參考 假設階段、單一來源新聞驅動、agent 之間有衝突者

## 8. 交易員介面與告警規格

### 8.1 交付物

- **盤前晨報** 昨日歸因、今日 regime 判讀、待觸發訊號清單、風險曝險快照、行事曆（財報、法說、總經數據）
- **訊號卡** 每個訊號一張，含方向、標的、進場區間、**失效條件**（最重要，寫明什麼情況代表這個判斷錯了）、預期持有期、信心度、支持證據連結、反方論點（來自 `RedTeamAgent`）
- **即時告警** 見下方分級
- **風險儀表板** 即時曝險、因子暴露、回撤路徑、限額使用率
- **盤後檢討** 損益歸因、訊號命中率、與預期偏離的個案

### 8.2 告警分級與抗疲勞

告警疲勞是這類系統最常見的死因。交易員關掉通知，系統就等於不存在。

- P0 立即 風控觸發、資料源中斷、部位對帳不符。管道為電話或即時通訊直接推播
- P1 15 分鐘內 訊號觸發、重大新聞影響持倉、限額接近上限
- P2 彙整 每小時或每日批次的市場觀察、新假設、次要異常
- 全部告警必須通過 去重（同一事件不重複發）、速率上限（每小時上限 N 則，超過改為彙整）、novelty 檢查（過去 24 小時已告知過的內容降級）
- 每則告警必須包含「所以呢」那一句話，說明建議動作或觀察重點，不得只丟數字

## 10. CLAUDE.md 內容

把以下區塊原樣存成 repo 根目錄的 `CLAUDE.md`。

```markdown
# 專案守則

## 語言
所有註解、文件、commit message 使用繁體中文。程式碼識別字用英文。

## 不可違反
1. LLM 產生的數值不得進入訊號計算或下單路徑。LLM 只做語意任務。
2. 任何讀取歷史資料的函式必須接受 `asof: datetime` 參數並據以過濾 `ingest_time`。沒有 asof 的資料存取函式一律視為 bug。
3. 回測執行期間禁止任何網路呼叫。偵測到即讓測試失敗。
4. 系統內部時間一律 UTC，只在展示層轉換為台北時間。
5. 所有參數放 configs/，程式碼中出現魔術數字即為 bug。
6. 資料品質檢查失敗時輸出 NO_TRADE 狀態，禁止填補後繼續。

## 開發流程
- 涉及數值計算的功能，先寫測試再寫實作。
- 每個 PR 必須附帶該功能的失效案例測試，不是只有 happy path。
- 新增特徵時同步新增性質測試，例如尺度不變性、平移不變性、缺值行為。
- 修改任何影響歷史訊號的邏輯，必須跑重現性測試確認舊訊號可重放。

## 品質門檻
- mypy --strict 通過
- ruff 通過
- 測試覆蓋率 src/features、src/backtest、src/risk 三個目錄不得低於 90%
- 每次提交前跑 `make check`

## 詢問時機
遇到以下情況停下來問，不要自行決定
- 需要引入新的外部資料源
- 需要放寬上述任一條不可違反規則
- 效能最佳化會犧牲可重現性
- 風控參數的具體數值
```

## 11. 分階段建置指令

每個 Phase 是一段可直接貼給 Claude Code 的指令。**前一階段驗收未過，不得進入下一階段。**

### Phase 0 骨架與型別系統

```
建立 trading-intel 專案骨架，按照 docs/SPEC.md 第 9 節的目錄結構。

具體要求
1. 用 uv 管理相依，Python 3.12
2. 在 src/core/types.py 定義核心型別，全部用 Pydantic v2
   - MarketEvent, NewsEvent, FeatureVector, Signal, OrderIntent, RiskVerdict
   - 每個型別必含 event_time 與 ingest_time 兩個 UTC datetime 欄位
   - Signal 必含 confidence, evidence_ids, half_life_days, invalidation_condition
3. 在 src/core/clock.py 實作可注入的時鐘介面，回測時用模擬時鐘，正式環境用系統時鐘。
   全專案禁止直接呼叫 datetime.now()，加一條 ruff 規則擋掉。
4. 建立 configs/ 的分層設定，用 pydantic-settings，環境變數覆寫
5. 設定 pytest、mypy strict、ruff、pre-commit hook、Makefile 的 check 目標
6. 寫 CLAUDE.md（內容見 SPEC 第 10 節）

驗收
- make check 全綠
- 有一個測試證明模擬時鐘可讓程式碼在任意歷史時點執行
- 有一個測試證明直接呼叫 datetime.now() 會被 lint 擋下
```

### Phase 1 資料層與品質閘門

```
實作 L0 與 L1，範圍先限定台股加美股日頻，不做即時 tick。

1. 沿用既有的 taiwan-fund-flow-lab 專案的 src/sector_rotation 資料層，
   以套件方式引入，不要重寫 TWSE 抓取與除權息修正邏輯。
   先讀那個專案的程式碼，列出可重用的模組清單再動手。
2. 實作 raw landing zone，原始 payload 以 Parquet 落地，永不覆寫，路徑含抓取時間戳
3. 實作企業行動引擎
   - 儲存未調整原始價 + 獨立的調整因子表
   - 提供 get_adjusted_prices(symbol, start, end, asof) 介面
   - 測試必須涵蓋 asof 在企業行動前後查詢同一段歷史，結果應不同
4. 建立 universe_membership 表與每日快照，含下市與處置股，確保無存活者偏誤
5. 實作 SPEC 3.3 的五類資料品質閘門，失敗時發出 DataQualityAlert 事件並將標的標記 NO_TRADE
6. 實作實體解析，別名表 + 模糊比對，信心度低於閾值進人工佇列
7. 用 Redis Streams 建立事件匯流排，含 consumer group 與重放能力

驗收
- 給定任一歷史日期，可完整重建當日的可交易宇宙
- 刻意注入五種髒資料（缺 bar、負量、high<low、重複、過期），
  五種都被閘門攔下且產生正確告警
- 事件流重放兩次產生相同結果的測試
```

### Phase 2 特徵與回測引擎（最關鍵的一階段）

```
實作 L2 特徵層與事件驅動回測引擎。這一階段的品質決定整個系統的可信度，
請優先正確性而非速度。

1. 特徵框架
   - 所有特徵為純函式，簽章 f(data, asof, **params) -> Series
   - 特徵註冊表，含版本號、相依欄位、預期值域
   - 實作橫斷面標準化（產業中性 + 市值中性）
2. 統計量模組（重要，不要用天真做法）
   - ADF 與 KPSS 定態檢定
   - OU 過程半衰期估計，視窗長度由半衰期決定
   - EWMA 與 Yang-Zhang 波動率估計
   - 未通過定態檢定的序列，均值回歸類特徵回傳 NaN 而非硬算
3. 事件驅動回測引擎
   - 逐事件推進，禁止向量化捷徑造成的隱性前視
   - 內建成本模型：台股證交稅 0.3%（當沖 0.15%）、手續費、
     平方根市場衝擊模型、保守滑價
   - 回測期間任何網路呼叫直接拋例外
4. 驗證協定模組
   - purged walk-forward with embargo
   - combinatorial purged CV
   - deflated Sharpe ratio（需接受累計試驗次數參數）
   - PBO 計算
   - 容量衰退曲線
5. 實作三個基準策略作為煙霧測試
   - 買進持有
   - 12-1 動量
   - 三大法人買超排序

驗收
- 前視偏誤測試：構造一個明顯用到未來資訊的特徵，回測引擎必須偵測並報錯
- 對已知答案的合成資料，回測損益與手算結果誤差在浮點誤差內
- 三個基準策略的績效數字落在文獻合理範圍
- 同一策略跑兩次，Sharpe 位元層級相同
```

### Phase 3 Agent 層

```
現在才開始接 LLM。實作 src/agents/。

1. 先寫 base.py 的通用契約
   - 統一的重試、逾時、schema 驗證、降級為 abstain
   - 成本與延遲記錄寫入 agent_calls 表
   - 每個 agent 的 token 預算與速率限制
   - 提示注入防護：外部文字包在資料標記內，輸出做列舉值白名單驗證
2. 只實作四個 LLM agent，每個都要有離線測試集（固定輸入對固定期望輸出）
   - NewsAnalystAgent，以 doc_type 涵蓋新聞、公告、財報、法說會、券商報告，
     共用同一份輸出 schema。事件分類法固定在 30 類以內，先產出分類法文件給我審核。
     事件級聚類去重與情緒計分寫成確定性程式碼，不另開 agent
   - HypothesisAgent，輸出必須含可證偽條件與驗證所需特徵
   - RedTeamAgent，八項固定檢查清單
   - LibrarianAgent，記錄所有測過的假設，LLM 僅用於語意相似度判重
3. 以下三項寫成純程式碼，不使用 LLM
   - src/models/regime.py 市場狀態分類
   - src/surface/attribution.py 損益歸因
   - src/agents/orchestrator.py 確定性狀態機，衝突時升級人工而非取平均

限制
- agent 的工具集中不得存在下單、改限額、關風控的能力
- agent 輸出的任何數值不得直接用於計算，只能作為分類標籤或權重的離散輸入

驗收
- 注入攻擊測試：在新聞內文中植入指令，agent 必須不執行且標記 suspicious
- 每個 agent 的離線測試集準確率達標
- 一致性測試：同輸入問三次，分歧度低於閾值
- 成本測試：模擬一整天的資料量，總 token 成本在預算內
```

## 12. 常見失敗模式的預防清單

- 資料清洗做得不夠，導致回測漂亮但實盤失效。**投入時間應該七成在資料與驗證，三成在模型**
- 過度依賴 LLM 做量化判斷，成本高且不穩定。LLM 的價值在非結構化資訊的結構化，不在算數
- 多重檢定失控，測一百個假設總有幾個看起來好。`LibrarianAgent` 與 deflated Sharpe 是唯一解藥
- 交易成本低估，尤其台股證交稅對高換手策略是致命的
- 告警太多導致被忽略
- 系統複雜到只有作者能維護。ADR 文件與 runbook 不是可選項
